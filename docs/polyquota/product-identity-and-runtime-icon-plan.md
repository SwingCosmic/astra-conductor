## 2. 图标构成

当前产品族图标已经定稿。PolyQuota 使用高饱和蓝色、紧凑卡片核心、120° 三等分节点和自下向上填色的三条用量卡片；GraphAgent 使用同族的高饱和紫色和正四面体投影结构。设计总览见 [`product-family-review.svg`](../common/icon-design/product-family-review.svg)。

PolyQuota 基础资产为 `polyquota.svg` 与 `polyquota-white.svg`，状态资产为 `polyquota-green.svg`、`polyquota-orange.svg`、`polyquota-red.svg` 和 `polyquota-unknown.svg`。SVG 均位于 `docs/common/icon-design`，是独立矢量资产，不依赖外部图片或字体。

应用派生资源位于 `apps/polyquota/assets/icons`。`polyquota.ico` 包含 16、20、24、32、40、48、64、256 像素八种尺寸，全部为标准图形（小尺寸由 256px 缩小），用于 EXE、安装器、卸载器和 Windows 窗口；基础版及绿、橙、红、灰状态均提供 256 像素 PNG，托盘另有 24 像素像素优化 PNG。`manifest.json` 保存母版与派生文件的 SHA-256，测试会拒绝母版更新后未重新生成的资源。

### 正式资产范围

| 场景 | 建议资产与行为 |
| --- | --- |
| UI 品牌、产品说明 | 基础蓝色 SVG |
| EXE、安装程序、卸载程序、快捷方式 | 基础蓝色多尺寸 ICO，静态品牌图标 |
| 运行中的窗口 | 同一套标准蓝色 ICO/PNG，不随额度换色 |
| 托盘 | 24px 像素优化 PNG，按全局额度档切换绿、橙、红、灰 |
| 任务栏 | 静态品牌图标；Windows 用原生进度条表达额度与档位色 |

正式 ICO 包含 16、20、24、32、40、48、64、256 像素，窗口与 ICO 始终使用标准图形，小尺寸由 256px 缩小即可。仅托盘 24px 使用像素对齐的超小布局，避免色块在通知区看不清。SVG 先作为母版评审，通过后再导出 PNG/ICO，并纳入开发与打包资源。绿、橙、红、灰状态 PNG 只供给托盘；不要用它们替换窗口、任务栏或 EXE 图标。

## 3. 透明托盘的处理方向

`apps/polyquota/src/main.ts` 已移除内联 SVG data URL，开发环境从 `assets/icons` 加载资源，安装后从 `resources/icons` 加载。窗口在 Windows 使用标准多尺寸 ICO，托盘使用 24 像素优化 PNG，并在资源解码为空时回退到 256 像素基础 PNG。任务栏按 AppUserModelID 取快捷方式图标。仅 NSIS 安装目录（与 EXE 同级存在 `Uninstall PolyQuota.exe`）调用 `app.setAppUserModelId("io.astraconductor.polyquota")`，与安装器写入的开始菜单快捷方式对齐。`pnpm dev` 和 `release/win-unpacked` 不设置该 ID、不创建或改写快捷方式，避免把已安装版本的任务栏分组和图标登记冲掉；未安装进程由 Windows 按 EXE 路径隐式分组，窗口与任务栏使用包内 ICO。

生成脚本通过 Electron 的透明离屏窗口直接渲染最终 SVG，并验证输出尺寸同时包含透明和可见像素。electron-builder 将整个图标目录复制到 `resources/icons`，并显式使用基础 ICO 作为应用、NSIS 安装器和卸载器图标。开发启动和 unpacked 应用烟测均已验证实际资源路径；打包后资源与源目录的文件清单及 SHA-256 完全一致，EXE 与安装器也能够提取出 PolyQuota 图标。

参考：[Electron nativeImage](https://www.electronjs.org/docs/latest/api/native-image#supported-formats)、[Electron Tray](https://www.electronjs.org/docs/latest/api/tray)。

## 4. Windows 运行时效果

运行时只做两件事：`Tray.setImage` 切换托盘状态图，`BrowserWindow.setProgressBar` 设置任务栏进度。不要调用 `setIcon` 或 `setOverlayIcon` 去换窗口/任务栏图标。EXE、快捷方式和窗口标题栏始终使用标准蓝色品牌图。

原生任务栏进度的 `mode` 提供 `normal`、`paused`、`error`，Windows 分别画成绿色、黄色和红色。产品橙色关注档映射为 `paused`；进度条颜色由系统绘制，文案仍写“关注”，不得把额度不足说成应用暂停或崩溃。进度长度按第 5 节综合剩余 R（0–100 的得分）映射：R ≥ 5 时为 R / 100；**R < 5 时始终画成 0.05**，避免红色进度细到看不见。档位仍按真实 R 判定（R = 0 也是 `error`）。可提供“任务栏显示额度进度”开关，默认开启；关闭只取消原生进度，托盘换色继续。

最小化但仍有任务栏按钮时继续显示进度；关闭并隐藏到托盘后只保留托盘状态，恢复窗口时按最新 R 重设进度。

参考：[Electron 窗口进度与图标 API](https://www.electronjs.org/docs/latest/api/browser-window#winsetprogressbarprogress-options)、[Microsoft 任务栏状态与颜色](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-itaskbarlist3-setprogressstate)。

## 5. 整体用量的语义

卡片仍按账号各自展示服务商配额。托盘换色和 Windows 任务栏进度使用**应用级综合剩余 R**；用量概览页头与标题+说明、刷新按钮同一行并排展示 session 与 week 两个环形进度。不再使用最低账号剩余，也不再使用 `overallRemainingPercentage`。计分按启用账号的**档位系数**加权。系数与展示名都来自 core 各家 `descriptor.ts` 的套餐表（`plans`）。运行时只做规范化后的精确匹配，不再按名称实时猜测。表中的 `multiplier` 可随时按观测调整，文档只固定推定规则，不抄具体数值。不拿 `quota.total` 当容量——多数服务商把百分比归一成 100 或 1000，跨账号不可比。

### 5.1 窗口族

配额按窗口时长归入三族。上限故意放宽，避免个别订阅把 24h session 或跨周窗口错分到更长族：

| 窗口族 | 判定 | 是否进入 R |
| --- | --- | --- |
| session（5h） | `windowSeconds` 有限且 **≤ 24 小时**（86400 秒）。3h、5h、6h、24h 的 session 都算这一族 | 计入 `S_5h` |
| week | 24 小时 < `windowSeconds` ≤ **14 天**（1209600 秒），或时长缺失但 key / 名称可识别为 weekly | 计入 `S_weekly` |
| 月 | `windowSeconds` 长于 14 天，或时长缺失但 key / 名称可识别为 monthly | **只用于折算成 week / session，不参与 R 的 min 比较** |

时长优先于 key。名为 `session` 但窗口为 30 天的配额归入月，只走折算。同一账号同一窗口族有多条配额时，取剩余比例最低且有效的一条。只使用账号主用量组里的窗口族；独立成组的模型限额（如 Claude 的 `model-limits`）即使窗口看起来像周用量，也不进入计分。

### 5.2 档位加权计分

N 为非禁用账号个数。每个启用账号有档位系数 `w`（正数），`W = Σ w`。`w` 由 `planMultiplier(provider, usage.plan)` 给出：命中套餐表则用该行当前的 `multiplier`，未命中则用中档 **5**。每个账号对某一窗口族的贡献为：

```text
得分 = r × 100 × w / W
```

`r` 是该账号该窗口族的剩余比例，范围 0–1。全部账号加总满分为 100。所有 `w` 相同时退化为按账号等权。session 与 week **分开加总**，得到 `S_5h` 和 `S_weekly`。月用量即使存在也不形成 `S_monthly`，不进入下面的 min：

```text
R = min(S_5h, S_weekly)
```

各账号卡片上的分项用量展示不变。R 驱动托盘色和任务栏进度；两个环形进度分别展示 `S_5h` 与 `S_weekly`。

**能拿到什么、不能拿什么：**

| 来源 | `usage.plan` 档位名 | 服务商内有序倍数 | `quota.total` 是否真实容量 |
| --- | --- | --- | --- |
| GLM | 有（Lite / Pro / Max） | 有：周积分 10000 / 60000 / 140000，即 **1 : 6 : 14** | 有时有积分绝对值；周窗口偶发只有百分比，此时 total 被写成 100 |
| Codex | 有（free / go / plus / prolite / pro / team / …） | 套餐名宣称相对 Plus 的倍率（实际可能打折）：Go≈免费、Plus=1、Pro 5x=5、Pro 20x=20 | 否，只有 `used_percent`，total 固定 100 |
| Claude | 有（tier / plan / Max 5x 等） | 官方 5h 相对 Pro：Pro=1、Max 5x=5、Max 20x=20 | 否，utilization 0–100，total 固定 100 |
| OpenCode Go | 固定产品名 | 无分档、无跨产品倍数 | 有，美元帽 $12 / $30 / $60，但只有一档产品 |
| Grok Build | 有 `subscriptionTier` | 无稳定公布倍数 | 否，只有 `creditUsagePercent` |
| Antigravity | 有（Free / Pro / Ultra 等） | 无公布倍数 | 否，`remainingFraction` 合成 total=1000 |

因此 `w` 与卡片上的套餐名都来自 core 套餐表，禁止用 remaining/total 绝对值做跨账号权重。写入或改表时的推定规则（**不是运行时逻辑**；多数 `inferred` 行仍是相对大小，未与官方额度核对）：

1. 服务商已公布相对倍数 → 用公布值。
2. 名称里带明确倍率（`5x`、`20x`）→ 用该数字。
3. 免费、超轻量（`free` / `go` / `starter` / `lite`）→ **0.1**。
4. 只有档位标识、无倍数：从低到高 **0.1 / 1 / 5 / 20**，对应 starter·lite / plus / pro / max·ultra。
5. 套餐未知或无公开信息 → **5**（中档）。

运行时：把 `usage.plan` 转成小写并折叠空白、`_`、`-` 后，与表中 `match` **整串相等**才命中。未列出的新字符串 `w = 5`，展示名用上游原文，不会再扫描名称里有没有 pro/max。当前各档 `multiplier` / `displayName` 只维护在对应 `descriptor.ts`，观测到相对用量变化时直接改表。

卡片套餐名取命中行的 `displayName`，经快照 `providers[].plans` 下发给前端。UI 不得再内置一套名称映射。档位名画成圆头标签（四角半径为标签高度的 50%），贴在供应商名称右侧；账号标识单独一行，避免长邮箱把档位截掉。

### 5.3 缺窗口时的折算

只允许从更长窗口折到更短窗口。缺更长窗口时该族按 `r = 1`（满分贡献），不从短窗口反推。折算用各家已公布的配额比例，**不按日历时长（5/168）折算**——5h 窗口实际给的量远大于一周的 5/168。

**周 → 5h 系数取 1/5。** 依据：

| 来源 | 5h / 周 | 口径 |
| --- | --- | --- |
| 智谱 GLM Coding Plan Lite / Pro / Max | **1/5** | 官方积分：2000/10000、12000/60000、28000/140000，三档相同 |
| GLM 历史 V2 套餐 | 1/5 | 官方约 80/400、400/2000、1600/8000 prompts |
| OpenCode Go | 2/5 | 产品美元帽 $12 / 5h 对 $30 / week |
| Claude Pro 实测（2026-10） | 约 1/12 | 一周约 12 个满 5h 窗口 |
| Claude Max 20x 实测 | 约 1/6.4 | 一周约 6.4 个满 5h 窗口 |
| Codex Plus | 约 1/3～1/2 | 官方只公布 5h 消息区间；社区称 2–3 个满窗口即可打空周额度 |
| 按日历 5 小时 / 168 小时 | 约 1/33.6 | 远小于所有已公布配额，弃用 |

采用 **1/5** 的原因：GLM 是目前唯一对 5h 与周都公布绝对额度、且各档比例一致的已接入服务商；1/5 约为日历比例的 6.7 倍。OpenCode Go 的 2/5 是美元帽，偏松。Claude 的 5h 更像突发节流、周池更大，若用 1/12 去折只有周用量的账号（如 Grok Build），要到周剩余很低才会压低 5h 分，偏乐观。Codex 周限额未公布，不单独定系数。

**没有 5h 族、有周族**（例如当前 Grok Build 只有周用量）：

```text
折算 5h 总量 = 周总量 / 5
```

剩余周用量大于该折算 5h 总量时，该账号 5h 的 `r = 1`。否则 `r = 剩余周用量 / 折算 5h 总量`。只有剩余比例时，等价为：周剩余大于 20% 则 5h 为 100%，否则 `r_5h = r_weekly × 5` 再封顶为 1。

**只有月用量**（尚未接入的小米 MiMo 即属此类；OpenCode Go 等已有 5h 与周的账号不要走这条）：

```text
折算周总量 = 月总量 / 4
r_weekly = 剩余月用量 / 折算周总量
```

即周用量按月度的 1/4 计。`r_weekly` 可以大于 1。计入 `S_weekly` 时封顶为 1。`r_weekly > 1`（周用量大于 100%）时该账号 5h 必为 100%。`r_weekly ≤ 1` 时再按上面的周→5h 规则折算 5h。月用量本身不参与 `R = min(S_5h, S_weekly)`。

同时有 session 与 week 时直接用真实剩余，不再折算。有 week 与月时忽略月（月只在缺少 week 时折算）。无限额度且未给出有效剩余比例的窗口族按 `r = 1` 计。

示例：两个启用账号且档位相同（`w` 均为 1）。A 的 5h 剩余 80%、周剩余 40%；B 的 5h 剩余 20%、周剩余 90%。

```text
S_5h     = 0.80×100/2 + 0.20×100/2 = 50
S_weekly = 0.40×100/2 + 0.90×100/2 = 65
R        = min(50, 65) = 50
```

若 A 为 GLM Lite（`w=1`）、B 为 GLM Max（`w=14`），`W=15`：

```text
S_5h     = 0.80×100×1/15 + 0.20×100×14/15 ≈ 24.0
S_weekly = 0.40×100×1/15 + 0.90×100×14/15 ≈ 86.7
R        = 24.0
```

再加一个只有周用量、周剩余 50%、`w=1` 的账号 C（与前两账号同权时 N=3）。C 的周剩余 50% > 20%，故 C 的 5h 为 100%：

```text
S_5h     = 0.80×100/3 + 0.20×100/3 + 1.00×100/3 ≈ 66.7
S_weekly = 0.40×100/3 + 0.90×100/3 + 0.50×100/3 ≈ 60.0
R        = 60.0
```

C 若周剩余 10%：`r_5h = 0.10 × 5 = 0.50`，该账号 5h 贡献 50%、周贡献 10%。

只有月用量、月剩余 50% 时：`r_weekly = 0.50 × 4 = 2.0`，周贡献按 100% 计，5h 为 100%。月剩余 10% 时：`r_weekly = 0.40`，周贡献 40%，5h 仍为 100%（40% > 20%）。月剩余 4% 时：`r_weekly = 0.16`，5h `r = 0.16 × 5 = 0.80`。

### 5.4 档位映射

托盘和任务栏按综合剩余 R 上色；每个环形进度按**自己那条得分**上色（`S_5h` 或 `S_weekly`），同一套 50 / 20 边界：

| 得分 | 托盘（用 R）/ 该环填色 | 原生任务栏进度（用 R） |
| --- | --- | --- |
| > 50 | 绿色：充足 | `normal`（系统绿），进度 R / 100 |
| 20 < 得分 ≤ 50 | 橙色：关注 | `paused`（系统黄），进度 R / 100 |
| 5 ≤ 得分 ≤ 20 | 红色：紧张 | `error`（系统红），进度 R / 100 |
| 0 ≤ 得分 < 5 | 红色：紧张 | `error`（系统红），**进度固定 0.05** |

例如 `S_5h = 80`、`S_weekly = 40` 时 R = 40：托盘和任务栏为橙色，5h 环仍为绿色、周环为橙色，可以看出是周用量把整体拉进关注档。R < 5 时环形进度和托盘仍按真实值（环可显示 0%）；只有 Windows 任务栏把长度抬到 5%，让红色可见。提示文案可以写“即将耗尽”。R 不是可合并的跨订阅余额，托盘不要写成“总剩余”。

### 5.5 用量概览环形进度

在用量概览页标题「用量概览」右侧并排两个略小的环形进度，左 session（5h）、右 week，避免只看到一个综合色却不知道是哪条窗口见底：

- 每个环心显示该条整数百分比（四舍五入），环下标注「5h」「周」。
- 左环弧长与填色跟 `S_5h`，右环跟 `S_weekly`；不套用任务栏的 5% 下限。
- 无有效得分时该环显示「—」，灰色。
- 无启用账号时两个环都是灰色空环，与托盘「暂无启用账号」一致。
- 数据不完整时，已算出的那条环可保留风险色，缺少数据的环为灰；不要用单独一个绿色综合环冒充完整结论。
- 两个环作为页头中间一组，与左侧标题+说明、右侧刷新按钮同一行，不塞进标题那一行；整体比单环方案略缩小。

### 5.6 数据规则

- R 是纯计算属性：每次快照都从当前启用账号的可见用量完整推导，不写入数据库，也不缓存上一次得分。启动、定时刷新、手动刷新、增删账号、启停账号都走同一函数；同一份用量反复计算得到同一结果。
- 禁用账号不参与，不计入 N。没有启用账号时托盘灰色、文案“暂无启用账号”，清除任务栏进度。
- 非有限数、超出 0–1 的 `r`、null、无快照都不作为有效比例。某账号两个窗口族都无法得到有效 `r`（含折算后）时，该账号视为数据不完整，不把它当成 0 去拉低 R；R 由其余启用账号的用量算出。
- 环形进度、托盘色和任务栏进度都跟这次算出的 `sessionScore` / `weeklyScore` / `remaining`，不用完整/不完整去改写档位。不完整只作为提示后缀。
- 刷新过程中保留上一次仍有效的状态，不把任务进度动画和额度进度混用。刷新失败单独标注，不用红色额度档冒充网络故障。

托盘提示示例：`PolyQuota · 综合剩余 50% · 关注`。数据不完整且已有 R 时为 `PolyQuota · 综合剩余 50% · 关注 · 部分数据待刷新`，不显示原始账号标识或凭证。
