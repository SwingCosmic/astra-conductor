## 1. 现状与落点

当前 PolyQuota 的 DI 已注册 CredentialVault，但凭据仍由产品直接保存密文，刷新互斥仅在进程内；GraphAgent 只有说明性占位目录。共享模式改为“应用申请许可、读取当前 payload、执行 provider 刷新、提交 broker”，供应商逻辑保留在应用侧。core 继续依赖 polyquota-contract，broker 采用中立存储协议，不导入现有 core 整包。

改动落点：

1. `packages/core/src/services/contracts.ts`、`ports.ts`：语义化 CredentialService，凭据存储与产品业务存储分离。
2. `credential-vault.ts`、`providers/*/adapter.ts`、`refresh-coordinator.ts`：收口 provisioner 提交、刷新与读取时重加密，保留私有后端兼容。
3. `apps/polyquota/src/runtime/`、`sqlite-storage.ts`：后端选择、产品绑定、导出/切换回执与安全缓存引用。
4. 新增 `packages/credentials`：无产品依赖的模型、密码格式、版本化协议/schema 与可选 SDK。
5. `packages/core` 的认证/刷新子集：刷新前申请跨进程许可，调用供应商后提交不透明结果。
6. 新增 `services/credential-broker`：独立服务入口、brokerctl/控制器、安装产物、自有密钥保管与凭据存储。
7. `apps/graph-agent`：最小可运行宿主、空白主页、设置页与共享客户端。

PolyQuota 保持当前 app name、userData 与 polyquota.db，以原安全身份解密已有凭据。

broker 使用 C# + 常规 .NET 自包含、目录式发布，采用受支持的 .NET LTS，关闭 AOT、裁剪与单文件打包，详见[设计第 2.6 节](./design.md#26-技术选型)。服务只实现密码存储、通用版本/许可协议、授权与生命周期；应用继续复用 TS provider，第三方自带实现。依赖图与网络边界检查须确认服务不依赖 apps、产品 contract/UI 或 provider。

## 2. 一阶段：单向建立共享

### 2.1 产品范围

- PolyQuota：首次导出、目标目录选择、迁移密钥展示、启用/重试共享、切回内置、恢复本次共享。不含通用导入、成功版本重新导出、换钥与共享库搬迁。
- GraphAgent：空白主页；设置页提供目录选择、密钥输入、验证预览、共享状态与失败重试，并支持对已导入且本地有 provider 实现的凭据手动刷新。不含导出、独立账号授权、独立活动内置凭据、聊天、Agent Loop、任务、工具与用量。
- 两个产品设置页均增加“凭据共享服务”一节，内容见[设计第 7.4 节](./design.md#74-独立发布按需安装与设置管理)。
- GraphAgent 宿主独立选型，复用共享模型与客户端，不复用 polyquota-ui 的结构与依赖。

### 2.2 实施步骤

1. **A1 broker 实现与独立测试**：建立独立仓库与可选 submodule，实现 C#/.NET 服务与控制器、schema、密码/存储/许可/元数据、CLI 与测试工具。完成条件：协议、并发与故障恢复测试通过，不依赖产品代码或下载地址。
2. **A2 本地复制安装验证**：复制完整 publish 目录安装，完成登记、发现、前台调试、卸载/重装与失败恢复。完成条件：不联网即可安装；干净 Windows（无预装 .NET 与两个产品）可运行；数据与密钥保留，安装位置不依赖源码路径。
3. **A3 独立 Release 发布**：将 A1/A2 产物发布到 GitHub Releases，提供版本、平台、兼容清单与发行校验信息。完成条件：已发布资产与测试产物一致，独立下载安装冒烟通过，真实地址与资产标识可用。
4. **A4 客户端适配与生产下载接线**：收口凭据调用，交付共享 SDK、安装检测/引导与设置管理组件，并按 A3 配置真实下载信息。完成条件：开发可复用本地安装，生产按需下载、校验与安装，provider 仍由应用执行。
5. **A5 PolyQuota 首次导出**：构建首次版本，回读验证后记住主密钥，向用户交付迁移密钥并显示导出成功。完成条件：导出成功与服务接管分别记录，失败候选可独立清理重建。
6. **A6 GraphAgent 最小壳与导入**：交付空白主页与设置页，接入 A4 安装管理、实际解密校验、脱敏确认与主密钥记忆。完成条件：错误密钥零导入，成功后进入导入就绪状态。
7. **A7 统一启用共享**：两侧接入共享客户端，实现记录级许可、幂等提交、事件补取与应用端刷新。完成条件：无长期 token 缓存，刷新先获许可，C1→C2→C3 在两侧及时可见。
8. **A8 PolyQuota 返回内置**：保存私有快照，完成本客户端解绑与密钥清理，提供独立刷新风险提示与本次共享重入。完成条件：其他客户端不中断，私有副本可独立刷新，重入需重新输入迁移密钥。

A1/A2 通过后才执行 A3；A3 资产核验通过后才在 A4 接入生产下载信息。

### 2.3 导出成功与共享建立

A1 同时交付 createdByClientId、lastUpdatedByClientId、`Record<string, string>` metadata 与不含 payload 的分页描述/筛选接口，归属字段由服务认证身份写入。A5 从 PolyQuota 的凭据能力生成 supportsUsage 等字符串声明；A7 接入描述变更后的筛选刷新，PolyQuota 只对 supportsUsage 为 `"true"` 且本地 provider 可用的记录按需读取秘密。元数据更新沿用记录许可与原子修订。GraphAgent/第三方仅有推理 API Key 的示例用于协议验收。

首次导出由独立服务产物中的短时导出工作进程或管理命令完成，持有与常驻 broker 相同的目录/vault 锁；已有服务在线时连接现有实例，不另启竞争写入者。

导出/导入入口先完成安装检测与必要的用户确认安装，再执行凭据流程。已有导出成功记录在重装后继续查询回执并重试切换，不重新导出。

GraphAgent 输入迁移密钥验证并记住主密钥后，两侧准备完成；由 PolyQuota 请求首次更新权交接，broker 记录回执并独立保存服务解锁材料，两侧据此启用共享。

从首次快照准备开始，冻结导出账号的凭据变更直至共享建立或用户取消切换，不阻止查看本地历史。导出与切换重试复用同一成功版本与已记住的主密钥；提交前复查来源水位，外部旧实例改动或远端刷新结果未知时停止接管。

明确失败保留“导出成功，可重试切换”；提交未知则保持冻结并查询原 operationId；broker 已接管但本地未接线时向前恢复。普通重启保留密钥，用户主动选择内置时才删除；密钥忘记或缓存损坏时重新执行导入验证。

### 2.4 PolyQuota 切回与本次共享恢复

用户确认独立刷新风险后，PolyQuota 将获准范围的共享凭据快照加密保存到私有后端，回读成功后切换本地运行后端、解绑自己的共享会话并清理自己的主密钥缓存。broker 不释放共享更新权，GraphAgent 与其他客户端继续正常刷新。尚未建立共享时直接保留原内置数据。

私有副本此后独立刷新，即使使用与共享侧相同的供应商凭据也允许，不强制重新授权；token 轮换、失效或相互影响的风险由用户承担，共享库内部仍保持单一写入者。

切换分别记录快照、本地启用、解绑与密钥清理的进度。远端解绑失败只使本客户端待清理会话最终过期；本地密钥删除失败保留 keyCleanupPending，重启继续处理。broker 不可达时允许使用已有可解密快照选择私有后端并提示数据时点；无副本则账号显示待导入或待授权。

PolyQuota 恢复本次共享时重新输入当前迁移密钥，验证后重新绑定共享侧当前凭据，其他客户端无需重新准备。私有副本更新不覆盖共享数据；合并或重新导出属于二阶段。

首次导出候选尚未成功时可清理重建；已成功的导出不能通过失败重试入口重写。迁移密钥交付失败须在初次导出流程中恢复；交付后丢失密钥且需要新客户端导入时，按二阶段密钥更新处理。

### 2.5 一阶段验收

- 默认内置行为不变；不导出时不创建共享库、不启动 broker，私有模式无隐式下载。
- GraphAgent 真实应用只含空白主页与设置页，使用自己的安全缓存与绑定，不打开 PolyQuota 业务数据库。
- broker 独立安装、手动启动与按需启动均不加载客户端代码；两个产品未安装时，独立 CLI 与第三方协议客户端仍可完成初始化、授权、连接与请求。
- .NET 自包含目录式发布携带所需 runtime 与 SQLite，关闭 AOT/裁剪/单文件；无预装 .NET 的干净 Windows 可运行，前台调试与服务运行复用同一业务入口。
- 主应用安装包不携带 broker/runtime；未安装时在共享入口与设置页提示安装，取消、离线或失败保留原后端与导出状态；服务断连不误判为未安装，设置页检测不拉起服务。
- Release 校验覆盖版本/平台/协议匹配、签名与摘要失败拒绝、解包路径约束、安装中断及双客户端并发安装/重装；下载失败不删除旧安装。
- A2 覆盖断网下从本地 publish 目录复制安装与重装，客户端通过安装登记发现服务；A4 使用实际 Release 完成生产下载验收。
- 设置页卸载影响全部相关 vault/客户端，排空后移除组件与启动注册并保留数据、密钥与绑定；重新下载安装恢复原服务身份，密钥不可用进入 LOCKED；产品卸载不卸载 broker。
- 导出、导入验证、统一接管、退出与重启连接形成闭环；秘密不进入 UI 普通响应、日志或事件；导出成功但 broker 启动或接线失败时，重启后可直接重试。
- 错误密钥、参数篡改、目录替换、身份不匹配、三个以上不同 clientId、并发服务启动、共享刷新串行与超时接替均通过；自定义 opaque payload 可完成存取/版本/许可验证，供应商请求只发生在客户端；受限第三方不能越权取主密钥或停止服务。
- 归属字段不可伪造：创建后来源固定，成功提交才改变最近更新者；失败释放、过期提交、幂等重放及版本复制/换钥不改写归属；payload、metadata、最近更新者、修订与事件原子一致。
- 分页列表与权限内筛选正确：仅支持推理的 API Key 被 PolyQuota 排除，其他客户端创建但 supportsUsage 为 `"true"` 的凭据仍可被发现，缺失标记视为未知；描述声明不能替代本地 provider 校验或绕过记录授权。
- metadata/metadataEquals 只接受字符串映射，拒绝嵌套对象、数组、布尔值、数字、null 与超限输入；覆盖 64 对、128 字节键、1 KiB 值、16 KiB 总编码及多字节字符边界；匹配区分大小写，`"TRUE"` 与 `" true "` 不等同于 `"true"`；按键设置/removeKeys 删除与未知扩展保留正确，普通刷新不清空 metadata。
- 同时刷新同一 C1 时仅一个应用取得许可并调用上游；手动更新到 C3 时在线订阅者自动读取新版本，事件丢失、重连、重复或乱序不会把 C3 覆盖回 C2。
- 网络错误、应用超时或供应商失败后主动 abortUpdate 进入 failed-released 并立即释放，原 payload/revision 不变；失败重试以新 operationId/许可重新排队，不占锁。
- 失败释放响应丢失可幂等重发；旧 abort 不释放接替者的锁，已成功提交的操作不被迟到失败报告回滚；释放请求无法送达时按 TTL 兜底，unknown 上游结果不阻止主动释放。
- 租约采用 TTL 30 秒、每 10 秒续期、最长占用 120 秒；临时掉线不立即释放，到期允许一个等待者接替，旧 fence 的迟到结果不写入，即使 baseRevision 未变；业务卡死、清理定时器未运行、到期竞争、反复重连或重启时，hardDeadline 不延长且不出现两个有效许可。
- markUpdateStarted 前后掉线、供应商迟到、提交成功响应丢失、接替者遇到旧 token 失效时，按 operationId 查询回执或正常重试/提示授权，未知结果不变成永久更新锁。
- 共享凭据不写客户端数据库或长期内存镜像，仅保留请求期间快照；主密钥缓存、脱敏元数据与修订可保留。
- PolyQuota 切回私有并忘记密钥后，其他客户端连接、修订和刷新继续正常；私有副本可独立刷新相同凭据，风险提示不强制重新授权；重入共享只读取共享当前记录，不覆盖共享数据。
- 初始版本各写入点故障不发布半成品；发布成功响应丢失时不误删 currentVersion；用户退出后没有密钥回填。
- Windows unpacked/安装版覆盖真实安全存储、迁移、重启与按需启动；provider 闭环使用经授权的测试账号。

### 2.6 独立服务生命周期验收

实现设计第 7 节的 STOPPED/STARTING/LOCKED/READY/IDLE/DRAINING/FAILED 状态。生命周期控制在 A1 实现、A2 本地安装验证，A3 发布前通过独立测试，产品场景在 A4—A8 联调验收：

1. 三个客户端同时 ensureRunning：控制器合并启动，只有一个进程取得 vault 锁，其余连接既有端点。
2. 一个客户端退出、切私有或崩溃：只释放它的会话，其他客户端无须重连、重新授权或停止刷新。
3. 全部客户端断开：排空或持久化操作与原截止时间，过期/未知记录不阻止空闲退出；新连接按剩余租约或超时接替规则处理。
4. 服务重启且最早导出客户端已卸载：使用服务自己的密钥保管器恢复，其他客户端按协议重连。
5. 密钥保管器暂不可用：状态为 LOCKED，独立管理端可解锁，不创建空库、不降级明文。
6. 进程崩溃或无响应：控制器确认旧服务退出并获得 OS 锁后恢复，许可原截止时间不重置，服务不双启。
7. 显式停止或升级：只接受管理权限；新请求停止、在途排空、回执持久化，最后释放锁。
8. 客户端卸载：保留独立服务、服务密钥与共享数据，服务卸载由单独管理操作执行。

一阶段完成即交付，不以双向导出、换钥、完整 Agent 功能或 macOS/Linux 适配为前置。

## 3. 二阶段：双向管理与版本更新

1. **双向导出/导入**：两个产品均可作为来源，处理本地独有账号与同身份冲突；验收双向建立同一共享服务，不按时间戳静默覆盖。
2. **双向后端/位置切换**：补齐 GraphAgent 私有后端往返及共享位置切换/搬迁；验收退出方独立刷新并忘记共享密钥，其他客户端不受影响。
3. **重新导出**：对已成功版本生成新候选，包含来源最新凭据与必要操作索引；验收构建期间旧版本持续可用，最终水位一致。
4. **密钥更新**：更新迁移密钥与存储主密钥，准备在线客户端缓存与离线重新导入；验收不原地覆盖旧密钥，未获准客户端不能自动取得新密钥。
5. **版本回收**：无引用后清理 retired/failed 版本及缓存；验收不误删当前版本，清理失败不回滚成功发布。

二阶段沿用设计的版本协议：`N → 构建 N+1 → 全量校验 → 原子发布 currentVersion → 延后清理 N`。失败只删除尚未发布的候选，并以新 attemptId/密钥重建；发布结果未知时先查控制库回执。

测试补充：并发导出/换钥、构建期间 token 轮换、每个写入与提交边界崩溃、服务/客户端密钥缓存部分准备失败、版本事件丢失/重连、旧版本读者未退出、发布后清理失败，以及任意客户端切回私有不停止其他共享绑定。新版主密钥发布后不允许降级接管。

二阶段只扩大凭据管理能力；GraphAgent 的聊天、任务与工具按 [GraphAgent 启动计划](../../../graph-agent/plan.md)另行实施。

## 4. 检查与完成口径

每阶段代码提交按仓库要求运行格式、类型检查、测试与构建；涉及 Electron/native/打包时运行 package，并覆盖相应宿主验证。密码协议采用标准向量与跨运行时互操作测试，恢复逻辑采用故障注入。

对外状态始终区分：设计已确定、首次导出成功、GraphAgent 导入就绪、broker 已接管、客户端已启用。当前仅完成这两份文档的整理，以上交付项均待实施。
