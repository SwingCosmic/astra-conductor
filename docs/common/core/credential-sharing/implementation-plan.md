## 1. 现状与落点

截至 A6—A8，PolyQuota 通过 CredentialService 提交凭据，默认使用内置 CredentialVault。已验证 GraphAgent 导入、两侧共享后端、跨进程刷新许可、PolyQuota 返回内置与重入。该阶段的 GraphAgent Electron 最小宿主只提供空白主页和设置页。共享刷新流程为“应用申请许可、读取当前 payload、执行 provider 刷新、提交 broker”。后续两个产品的凭据页面从各自的 Hono 应用访问该流程，产品前后端契约与 broker 存储协议分别演进。

A1—A8 已实施的代码落点如下。迁移后的包名和宿主边界遵循[项目架构](../../../architecture.md)。

1. `packages/core/src/services/contracts.ts`、`ports.ts`：语义化 CredentialService，凭据存储与产品业务存储分离。
2. `credential-vault.ts`、`providers/*/adapter.ts`、`refresh-coordinator.ts`：收口 provisioner 提交、刷新与读取时重加密，保留私有后端兼容。
3. `apps/polyquota/src/runtime/`、`sqlite-storage.ts`：后端选择、产品绑定、导出/切换回执与安全缓存引用。
4. `packages/credentials`：无产品依赖的模型、密码格式、版本化协议客户端、记录许可与事件 SDK；Windows 本地组件管理与连接宿主已在 B1 从原 `packages/credential-host` 合入同包 `/host/windows` 子入口，无 Electron/UI 依赖。
5. `packages/core` 的认证/刷新子集：刷新前申请跨进程许可，调用供应商后提交不透明结果。
6. 独立 `astra-credential-broker` 仓库：服务入口、brokerctl/控制器、安装产物、自有密钥保管与凭据存储；产品只消费独立产物与协议，不引用其源码作为运行时依赖。
7. `apps/graph-agent`：最小可运行宿主、空白主页、设置页与共享客户端。

PolyQuota 保持当前 app name、userData 与 polyquota.db，以原安全身份解密已有凭据。

broker 使用 C# + 常规 .NET 自包含、目录式发布，采用受支持的 .NET LTS，关闭 AOT、裁剪与单文件打包，详见[设计第 2.6 节](./design.md#26-技术选型)。服务只实现密码存储、通用版本/许可协议、授权与生命周期；应用继续复用 TS provider，第三方自带实现。依赖图与网络边界检查须确认服务不依赖 apps、产品 contract/UI 或 provider。

## 2. 一阶段：单向建立共享

### 2.1 产品范围

- PolyQuota：首次导出、目标目录选择、迁移密钥展示、启用/重试共享、切回内置、恢复本次共享。不含通用导入、成功版本重新导出、换钥与共享库搬迁。
- GraphAgent：空白主页；设置页提供目录选择、密钥输入、验证预览、共享状态与失败重试，并支持对已导入且本地有 provider 实现的凭据手动刷新。不含导出、独立账号授权、独立活动内置凭据、聊天、Agent Loop、任务、工具与用量。
- 两个产品设置页均增加“凭据共享服务”一节，内容见[设计第 7.4 节](./design.md#74-独立发布按需安装与设置管理)。

### 2.2 实施步骤

1. **A1 broker 实现与独立测试**：建立独立仓库与可选 submodule，实现 C#/.NET 服务与控制器、schema、密码/存储/许可/元数据、CLI 与测试工具。完成条件：协议、并发与故障恢复测试通过，不依赖产品代码或下载地址。
2. **A2 本地复制安装验证**：复制完整 publish 目录安装，完成登记、发现、前台调试、卸载/重装与失败恢复。完成条件：不联网即可安装；干净 Windows（无预装 .NET 与两个产品）可运行；数据与密钥保留，安装位置不依赖源码路径。
3. **A3 本地包安装与组件管理（已实现并通过本机验证）**：先确定客户端预计使用的下载暂存目录及版本/平台布局，由开发者手动将打包好的完整自包含产物放到该目录。安装入口直接消费本地已就绪产物，完成校验、必要的解包、安装登记、只读检测、卸载/重装与失败恢复；复用 A2 的独立安装机制。完成条件：不联网、不依赖 Release 即可从该目录安装，安装后通过登记发现服务，实际运行位置独立于下载暂存目录与源码目录，已有兼容安装可直接复用。
4. **A4 客户端适配与共享接线（导出侧已实现）**：收口凭据调用，交付共享 SDK、安装检测/引导与设置管理组件，连接 A3 安装并登记的 broker。完成条件：本地安装、发现、按需启动、协议连接与安全状态反馈通过，provider 仍由应用执行；A5—A8 可基于此继续接入与联调，无需真实下载地址或 Release。
5. **A5 PolyQuota 首次导出（已实现并通过本机验证）**：构建首次版本，回读验证后记住主密钥，向用户交付迁移密钥并显示导出成功。完成条件：导出成功与服务接管分别记录，失败候选可独立清理重建。
6. **A6 GraphAgent 最小壳与导入（已实现并通过本机闭环）**：交付空白主页与设置页，接入 A3/A4 安装管理与共享客户端、实际解密校验、脱敏确认与主密钥记忆。完成条件：错误密钥零导入，成功后进入导入就绪状态。
7. **A7 统一启用共享（已实现并通过本机闭环）**：两侧接入共享客户端，实现记录级许可、幂等提交、事件补取与应用端刷新。完成条件：无长期 token 缓存，刷新先获许可，C1→C2→C3 在两侧及时可见。
8. **A8 PolyQuota 返回内置（已实现并通过本机闭环）**：保存私有快照，完成本客户端解绑与密钥清理，提供独立刷新风险提示与本次共享重入。完成条件：其他客户端不中断，私有副本可独立刷新，重入需重新输入迁移密钥。

一阶段在 A8 的本机单向共享闭环收口。独立 Release 与生产下载接入在二阶段 B4 交付。[A6—A8 本机实施与验收](./a6-a8-sharing-implementation.md)

A3 中的“预计下载目录”是产物暂存入口，不是 broker 的运行目录或共享数据目录；具体路径及布局在实现时通过统一配置确定，手动放置与后续下载使用同一约定。手动放置的是完整打包产物及本地校验清单，不逐个拼装运行文件；本地清单记录版本、平台、协议兼容范围及文件摘要，安装时检查来源、完整性、依赖与安全解包路径。开发本地产物明确标记来源，不伪装为已通过 Release 发行签名验证。B4 负责获取并验证可信发行资产，再交给同一安装入口；不因本地路径可用而放宽生产发行校验。

验收分别记录“本地安装完成”“客户端适配完成”“产品共享闭环完成”“生产下载完成”。B4 未完成时，可继续并完成本地接入验收；面向用户的生产自动下载安装能力须待 B4 通过后交付。

### 2.3 导出成功与共享建立

A1 交付 broker 侧的归属、字符串 metadata 与描述筛选；A5 由 PolyQuota 生成 `supportsUsage` 等字符串声明；A7 按描述变更刷新，仅对 `supportsUsage === "true"` 且本地 provider 可用的记录读取秘密。首次导出由独立工作进程或管理命令在同一目录/vault 锁下完成；已有服务在线时连接现有实例。

导出/导入入口先完成安装检测与必要的用户确认安装。已有导出成功记录在重装后继续查询回执并重试切换，不重新导出。GraphAgent 验证迁移密钥并记住主密钥后，两侧准备完成；PolyQuota 请求首次更新权交接，broker 记录回执并保存解锁材料，两侧据此启用共享。

从首次快照准备开始，冻结导出账号的凭据变更直至共享建立或用户取消，不阻止查看本地历史。导出与切换重试复用同一成功版本和已记住的主密钥；提交前复查来源水位，外部旧实例改动或远端刷新结果未知时停止接管。明确失败保留“导出成功，可重试切换”；提交未知则保持冻结并查询原 operationId；broker 已接管但本地未接线时向前恢复。普通重启保留密钥，用户主动切回内置时才删除；密钥忘记或缓存损坏时重新执行导入验证。

### 2.4 PolyQuota 切回与本次共享恢复

用户确认独立刷新风险后，PolyQuota 将获准范围的共享凭据快照加密保存到私有后端，回读成功后切换本地运行后端、解绑本客户端共享会话并清理主密钥缓存。broker 不释放共享更新权，其他客户端继续刷新；尚未建立共享时直接保留原内置数据。私有副本此后可独立刷新，风险由用户承担，共享库内部仍保持单一写入者。

切换分别记录快照、本地启用、解绑与密钥清理进度。远端解绑失败只使本客户端待清理会话最终过期；本地密钥删除失败保留 keyCleanupPending，重启继续处理。broker 不可达时允许使用已有可解密快照选择私有后端并提示数据时点；无副本则显示待导入或待授权。恢复共享时重新输入当前迁移密钥，验证后绑定共享当前记录；私有副本更新不覆盖共享数据，合并与重新导出归二阶段。

首次导出候选尚未成功时可清理重建；已成功的导出不能通过失败重试入口重写。迁移密钥交付失败须在初次导出流程中恢复；交付后丢失密钥且需要新客户端导入时，按二阶段密钥更新处理。

### 2.5 一阶段验收

- 默认内置行为不变；不导出时不创建共享库、不启动 broker，私有模式无隐式下载。
- GraphAgent 真实应用只含空白主页与设置页，使用自己的安全缓存与绑定，不打开 PolyQuota 业务数据库。
- broker 独立安装、手动启动与按需启动均不加载客户端代码；两个产品未安装时，独立 CLI 与第三方协议客户端仍可完成初始化、授权、连接与请求。
- .NET 自包含目录式发布携带所需 runtime 与 SQLite，关闭 AOT/裁剪/单文件；无预装 .NET 的干净 Windows 可运行，前台调试与服务运行复用同一业务入口。
- 主应用安装包不携带 broker/runtime；未安装时在共享入口与设置页提示安装，取消、离线或失败保留原后端与导出状态；服务断连不误判为未安装，设置页检测不拉起服务。
- A2 覆盖断网下从本地 publish 目录复制安装与重装。A3 校验手动暂存的完整产物、兼容性、文件摘要和安装恢复。A4 及 A5—A8 通过安装登记发现并接入服务。实际 Release 的签名与生产下载单列在二阶段 B4 验收。
- 设置页卸载影响全部相关 vault/客户端，排空后移除组件与启动注册并保留数据、密钥与绑定；重新下载安装恢复原服务身份，密钥不可用进入 LOCKED；产品卸载不卸载 broker。
- 导出、导入验证、统一接管、退出与重启连接形成闭环；秘密不进入 UI 普通响应、日志或事件；导出成功但 broker 启动或接线失败时，重启后可直接重试。
- 错误密钥、参数篡改、目录替换、身份不匹配、三个以上不同 clientId、并发服务启动、共享刷新串行与超时接替均通过；自定义 opaque payload 可完成存取/版本/许可验证，供应商请求只发生在客户端；受限第三方不能越权取主密钥或停止服务。
- 归属字段不可伪造：创建后来源固定，成功提交才改变最近更新者；失败释放、过期提交、幂等重放及版本复制/换钥不改写归属；payload、metadata、最近更新者、修订与事件原子一致。
- 分页列表与权限内筛选正确：仅支持推理的 API Key 被 PolyQuota 排除，其他客户端创建但 supportsUsage 为 `"true"` 的凭据仍可被发现，缺失标记视为未知；描述声明不能替代本地 provider 校验或绕过记录授权。
- metadata/metadataEquals 只接受字符串映射，拒绝嵌套对象、数组、布尔值、数字、null 与超限输入；覆盖 64 对、128 字节键、1 KiB 值、16 KiB 总编码及多字节字符边界；匹配区分大小写，`"TRUE"` 与 `" true "` 不等同于 `"true"`；按键设置/removeKeys 删除与未知扩展保留正确，普通刷新不清空 metadata。
- 同时刷新同一 C1 时仅一个应用取得许可并调用上游；手动更新到 C3 时在线订阅者自动读取新版本，事件丢失、重连、重复或乱序不会把 C3 覆盖回 C2。
- 网络错误、应用超时或供应商失败后主动 abortUpdate 进入 failed-released 并立即释放，原 payload/revision 不变；失败重试以新 operationId/许可重新排队，不占锁。
- 失败释放响应丢失可幂等重发；旧 abort 不释放接替者的锁，已成功提交的操作不被迟到失败报告回滚；释放请求无法送达时按 TTL 兜底，unknown 上游结果不阻止主动释放。
- 租约采用 TTL 30 秒、每 10 秒续期、最长占用 120 秒；临时掉线不立即释放，到期允许一个等待者接替，旧 fence 的迟到结果不写入，即使 baseRevision 未变；业务卡死、清理定时器未运行、到期竞争、反复重连或重启时，hardDeadline 不延长且不出现两个有效许可。
- markUpdateStarted 前后掉线、供应商迟到、提交成功响应丢失、接替者遇到旧 token 失效时，按 operationId 查询回执或正常重试/提示授权，未知结果不变成永久更新锁。
- 共享凭据不写客户端数据库或长期内存镜像，仅保留请求期间快照；主密钥缓存、脱敏元数据与修订可保留。
- PolyQuota 切回私有并忘记密钥后，其他客户端连接、修订和刷新继续正常；私有副本可独立刷新相同凭据，风险提示不强制重新授权；重入共享只读取共享当前记录，不覆盖共享数据。
- 初始版本各写入点故障不发布半成品；发布成功响应丢失时不误删 currentVersion；用户退出后没有密钥回填。
- Windows unpacked/安装版覆盖真实安全存储、迁移、重启与按需启动；provider 闭环使用经授权的测试账号。

### 2.6 独立服务生命周期验收

实现[设计第 7 节](./design.md#7-broker-生命周期)的 STOPPED/STARTING/LOCKED/READY/IDLE/DRAINING/FAILED 状态。生命周期控制在 A1 实现、A2 本地安装验证，B4 发布前通过独立测试，产品场景基于 A3/A4 本地安装与适配在 A5—A8 联调验收，无需等待 B4：

1. 三个客户端同时 ensureRunning：控制器合并启动，只有一个进程取得 vault 锁，其余连接既有端点。
2. 一个客户端退出、切私有或崩溃：只释放它的会话，其他客户端无须重连、重新授权或停止刷新。
3. 全部客户端断开：排空或持久化操作与原截止时间，过期/未知记录不阻止空闲退出；新连接按剩余租约或超时接替规则处理。
4. 服务重启且最早导出客户端已卸载：使用服务自己的密钥保管器恢复，其他客户端按协议重连。
5. 密钥保管器暂不可用：状态为 LOCKED，独立管理端可解锁，不创建空库、不降级明文。
6. 进程崩溃或无响应：控制器确认旧服务退出并获得 OS 锁后恢复，许可原截止时间不重置，服务不双启。
7. 显式停止或升级：只接受管理权限；新请求停止、在途排空、回执持久化，最后释放锁。
8. 客户端卸载：保留独立服务、服务密钥与共享数据，服务卸载由单独管理操作执行。

一阶段完成即交付，不以双向导出、换钥、完整 Agent 功能或 macOS/Linux 适配为前置。

## 3. 二阶段：双向管理与版本更新

B1 已完成合包，并用一期本地 broker 通过安装/重装及 17 项单向共享闭环回归，作为后续项目架构调整的前置。B2—B6 待实施。B2/B3 在供应商平台第一阶段提供共用凭据页面、两款产品的 Hono 入口和 GraphAgent 可写的私有后端后即可接线。最终双向验收中的普通 Key、路由编辑及缓存失效使用平台第二阶段的 Core 能力和第三阶段的页面入口，在相关入口可用时与平台第三阶段并行联调。B5 使用平台第二阶段交付的元数据转换器及旧格式夹具。其它项目结构调整和共用页面建设归[供应商平台三阶段实施方案](../provider-platform-implementation-plan.md)。

### B1 合并凭据包（已完成）

2. 将两款产品的 Windows 适配器及测试切到新子入口。更新 workspace 依赖、lockfile、根级和产品的构建/启动/测试/打包脚本。独立构建验证两个入口在产物中可解析后，移除旧包目录与对旧包名的依赖。
3. 使用与一期相同的本地 broker 验证兼容性。SDK 根入口可独立导入，新 Windows 子入口通过组件检测、安装、发现、连接与重装回归。复测已有迁移包、vault、客户端登记和 A6—A8 双进程闭环。合包只迁移 TypeScript 模块，不触发 broker 版本发布、换钥或共享库重建。

2026-11-07 完成上述迁移。SDK 通过临时外部 consumer 独立构建与类型消费验证，436 项测试、类型检查、全量构建和两产品 NSIS 打包通过；0.2.0 本地 broker（协议 1、API level 2）通过安装/重装和 17 项双进程闭环。具体落点、命令及打包结果见 [B1 实施记录](./b1-credentials-package-implementation.md)。

### 双向导出与存储切换

1. **B2 导出、导入与交接。** 将现有 PolyQuota 导出流程与 GraphAgent 接收流程抽取为两端均可调用的宿主服务。保留各自的加密存储、系统目录选择和应用绑定。GraphAgent 能从自己的私有账号导出，PolyQuota 能实际解密并确认导入。遇到同身份账号先展示冲突并记录用户的选择。接收侧已有私有账号保留自己的副本，重入时读取 broker 的最新修订。
2. **B2 共享写入。** 两端接入获准的共享新增、替换及删除。`@astra-conductor/credentials` 封装通用 RPC、许可和版本回执，Windows 宿主通过同包 `/host/windows` 子入口处理组件检查、发现及存量授权更新。首次交接前冻结、排空来源写入并持久化提交意图，broker 接管后两端各自接线。日常刷新沿用记录级许可和 fence。
3. **B3 切回、重入与位置切换。** 在线切回按获准的完整绑定生成一致快照，加密落盘、回读验证并对账删除及撤权，然后持久切换并清理本端会话与主密钥。区分所选后端、实际后端、导入就绪、更新权、待清理和待升级状态。切回只解除本端绑定，另一端继续按原共享版本读写。重新加入时输入当前迁移密钥，以共享侧当前修订恢复绑定。共享位置变更时核对 vault 身份、版本和双方登记路径，再恢复读写。通过下文双端验收矩阵的前六项后，记录 B3 双向共享完成。

### B4 独立发布与生产下载

B3 的双向共享实测通过后，将该次验收使用的独立 broker 自包含产物发布到 GitHub Releases。提供版本、平台、兼容清单、摘要及发行签名。核对线上资产与已验产物后，给两款产品配置真实下载源和版本选择，接通下载进度、校验与失败重试，并复用 A3 安装/重装入口。

使用实际 Release 分别在两端验证首次下载、校验、安装、共享接入和重装。覆盖平台、协议或 API level 不兼容、签名或摘要错误、解包路径约束、并发安装及下载中断后保留旧安装。生产分发记录包含 Release 标识、资产摘要和两端结果。后续 B5/B6 如需新的 broker 能力，按实际协议与 API 变更发布对应版本。

### 元数据升级触发重新导出

**B5。** 现有初始化只允许发布第一个版本。实施需要在独立 broker 增加候选版本构建、维护屏障、版本发布与回执查询能力，由 SDK 和两个宿主接入。若增加必需 RPC，相应提高所需 API level，在开启升级前核实已安装及运行组件的能力。[凭据共享设计第 6 节](./design.md#6-数据版本与一致性)

1. **识别升级。** 为产品管理的导出元数据定义格式版本，在受完整性保护的版本信息中记载。已发布旧库缺少该标记时，按其已知旧格式读取。两端打开同一库均能识别“需要重新导出”及目标格式。只有获准处理完整版本的一端才能发起。普通单条记录修改或 token 刷新只增加记录修订。
2. **构建候选。** 以当前权威版本 N 及其已提交修订水位为源。应用侧用 Core 提供的元数据转换器更新已识别记录，broker 负责通用存储与许可。候选 N+1 保留 vault 身份、记录 ID、归属、修订连续性、未知扩展/不透明记录、幂等回执索引和事件水位。版本复制或重加密保留记录已有的创建者与最近更新者。已删除记录不得复活。N+1 表示后继版本，实际使用独立的版本和尝试标识。旧私有快照不得覆盖共享侧更新。
3. **校验并发布。** 构建期间 N 可用。发布前短暂阻止新写入和新许可，排空或 fence 在途许可，追平并发更新。校验新记录清单、迁移包实际解密结果、必要的密钥槽及回读，再在控制库一个事务中校验基础版本、发布唯一 `currentVersion` 和回执。既有 broker 更新权不因重新导出而重置。按新版本的密钥交付规则验证在线客户端与 broker 的持久缓存，离线客户端重连后核验版本并按需重新导入。
4. **恢复与收尾。** 确认发布前失败后，可清理候选并使用新的 attemptId 和密钥重建，N 继续工作。发布响应丢失时先查原操作回执，已发布则向前恢复两端绑定。写入许可和提交绑定存储版本，旧版本未完成的提交不能写入新库。客户端只修改自己能够完整读写的记录格式。双端同时发起、重复点击、重启或已升级库再次打开，同一基础版本至多成功发布一个目标版本。旧版本在读者和恢复操作释放后回收。

### 密钥更新与版本回收

**B6。** 基于 B5 的版本协议支持独立更新迁移密钥与存储主密钥。发布前准备并验证在线客户端及服务的新密钥槽，保留旧槽供恢复。离线客户端重连后按新版本重新导入，未获准的客户端不能自动取得新密钥。版本发布后待旧读者和恢复操作释放，再回收 retired/failed 版本和关联缓存。清理失败可重试，已成功发布的版本号不复用。

### 双端验收矩阵

矩阵按交付节点验收。前六项使用本地完整 broker，作为 B2/B3 的双向共享发布门槛。最后两项使用具备升级能力的 broker，在 B5 验收。每行使用独立产品 profile、适用于宿主的持久密钥保护与虚构凭据。桌面组合覆盖真实 safeStorage/DPAPI。另以 GraphAgent 独立 Node/Web 和 PolyQuota Electron 运行双向流程，验证从浏览器调用相同 Hono API、服务端持久加密和重启恢复。正向、反向首次建立共享分别从空 vault 开始。每次操作核对两端界面、持久绑定、实际读写后端、共享版本、修订和密钥清理状态。供应商 HTTP 使用可记录请求的受控实现。

| 场景 | 操作与通过标准 |
| --- | --- |
| 正向建立 | PolyQuota 私有导出 → GraphAgent 验证和确认 → 两端交接启用共享。错误密钥或取消预览无持久副作用。共享刷新在另一端可见，两端重启后使用相同 vault 与当前版本 |
| 反向建立 | GraphAgent 创建私有账号并导出 → PolyQuota 核对脱敏预览、处理同身份冲突并导入 → 两端共享。测试订阅账号和无订阅 Key，后者可管理和回读，其用量请求数为零 |
| 单端切回与重入 | 从双共享分别让 PolyQuota、GraphAgent 单独切回。退出方得到已验证私有副本并忘记自身密钥，重启仍为私有。另一端保持共享并继续提交。退出方再用迁移密钥重入，读到另一端刚提交的修订，后者无需再次准备或交接 |
| 双端切回与重入 | 依次达到两端均私有，分别修改私有副本，再以相反顺序逐一重入。错误密钥保留私有选择，正确密钥读取当前共享版本。断言两个私有改动均未自动回写；最后两端均共享且可交换修订 |
| 离线、故障与位置 | broker 离线不自动切私有。显式切回时，有已验证副本须显示时点，无副本则显示待导入/授权。对切换中断、解绑失败、密钥删除失败按原操作恢复。变更已登记共享位置时核对 vault 身份与版本，两端重启后使用选定位置，选错目录不破坏原绑定 |
| 共享增删改与快照 | 一端创建普通 Key、改协议地址或替换秘密，另一端收到失效通知后按新修订读取，旧地址的目录失效。同修订并发刷新只提交一次。删除或失去访问权后切私有，快照与清单一致。普通 Key、路由、具名秘密均能回读验证 |
| 从旧版 N 升级成功 | 用包含 Core 提供的旧格式夹具的真实已发布库 N，保留原始副本，每个方向在独立副本上运行。分别以两款产品为发起端打开 N，由格式差异触发重新导出。升级中让另一端刷新一条记录。校验 N+1 的用途筛选、未知字段、最新秘密、修订/事件水位，并由接收端实际解密新迁移包。两端重启及离线端重入后都能读取 N+1，再次检测无待升级项 |
| 升级中断与幂等 | 注入候选校验失败、发布响应丢失、双端同时发起、发布后客户端接线失败。失败候选不替换 N，未知结果按原回执恢复。成功时只出现一个后继版本，过时写入被拒，旧缓存清理失败可重试且不会倒退版本 |

B5/B6 另验并发重新导出与换钥、版本写入及提交边界崩溃、密钥缓存部分准备失败、版本事件丢失或重连、旧版本读者仍在线，以及发布后清理失败。新版主密钥发布后，旧版本不能降级接管。

扩展现有 `pnpm test:credential-sharing-loop --publish <完整发布目录>`，从两个产品的正式凭据页面发起操作。分别保留正向、反向、切换与版本升级结果及脱敏截图，记录组件版本、API level、夹具格式和通过的场景。真实双进程用例通过后再将对应场景标记为已验收。

2026-11-07 使用 0.2.0 本地 broker（协议 1、API level 2）、两个隔离 Electron 进程和真实系统密钥存储复测现有闭环，**17 项全部通过**，实际供应商网络请求为 0。覆盖 PolyQuota 导出、GraphAgent 导入、双方刷新、PolyQuota 切回和重新加入。GraphAgent 作为来源、GraphAgent 私有往返和已发布库的升级属于本专项二阶段，待实现并实测。[现有闭环用例](../../../../apps/polyquota/test/credential-sharing-loop-electron.mjs)

## 4. 检查与完成口径

每阶段代码提交按仓库要求运行格式、类型检查、测试与构建；涉及 Electron/native/打包时运行 package，并覆盖相应宿主验证。密码协议采用标准向量与跨运行时互操作测试，恢复逻辑采用故障注入。

对外状态始终区分：设计已确定、首次导出成功、GraphAgent 导入就绪、broker 已接管、客户端已启用。当前后端通过 selectedBackend/activeBackend 分别表达持久选择与实际接线；首次导出先保留 private 与冻结状态，交接并接线成功后才启用 shared。服务失联保留共享选择并报告不可用，不静默切回旧私有凭据。一期实测范围见 [A6—A8 实施说明](./a6-a8-sharing-implementation.md)。
