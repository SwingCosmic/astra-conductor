本报告研究 DeepSeek Harness（下文简称 DSH）如何通过插件把服务定义、提供者和消费者解耦。PolyQuota 不需要成为通用插件宿主，但 DSH 对注册所有权、动态替换、冲突处理和能力闭环的约束可以直接改善服务商实现绑定。

## 1. 结论

DSH 的基本单位不是“预置服务商配置”，而是“在一个有生命周期的上下文中注册能力的插件”。模型适配器、工具、会话、Agent Loop 和设置扩展都通过同一套机制组合；插件卸载时，它贡献的注册项随 effect 一起释放。

它最值得 PolyQuota 借鉴的不是任意插件装载，而是以下注册语义：

1. 一个稳定路由在任一时刻只允许一个实现拥有；
2. 多路由注册必须先完整校验，再全有或全无地提交；
3. 注册句柄负责释放所有权，并允许同一实现原子替换自己的路由集合；
4. 能力元数据和最终调用必须来自同一代实现，避免配置更新期间交叉配对；
5. 不支持的能力明确报错，不能静默忽略；
6. 目录声明与已经激活的实现可以分开，前端能看见可配置但尚未启用的服务商。

PolyQuota 首阶段应实现受控的内部注册表，而不是引入 DSH 的通用插件加载器和热替换体系。

## 2. 全插件组合模型

`docs/architecture.md` 将 DSH 定义为由 Cordis 插件组合的 Agent Harness。基础服务只声明能力接口，实际提供者由配置中的插件行安装。Profile、Bundle 和有序 Patch 层决定最终启用哪些插件及其参数。

三个角色保持分离：

- Service Definition：定义稳定能力与事件；
- Provider：向上下文注册实现；
- Consumer：只依赖服务，不依赖提供者包。

插件安装、事件监听和注册都被视为可撤销 effect。配置变化或插件卸载时，Cordis 负责依次清理这些 effect。`ctx.inject()` 还能在依赖服务出现、消失或替换时重新执行消费插件。

这种模型允许替换任意部分，但也意味着系统必须精确管理所有权与销毁顺序。

## 3. LLM 适配器契约

`packages/llm/llm/src/index.ts` 定义 `LlmAdapter` 和 `LlmRuntime`。适配器的必需方法只有流式调用，其他能力按统一协议提供：

- `providerInfo(provider)`：路由展示信息；
- `providerRetryPolicy(provider)`：服务商重试策略；
- `imageRequestPricing(provider, model)`：可选计价差异；
- `listModels(provider)`：可发现模型目录；
- `resolveModel(provider, model, signal)`：精确模型能力；
- `prepareCall(provider, model, signal)`：把能力解析与后续调用绑定到同一代适配器；
- `stream(options)`：最终协议调用。

`packages/llm/llm/src/types.ts` 用统一类型表达服务商、模型、上下文、推理选项和流式分块。差异没有被完全抹平：推理强度是适配器拥有的稳定不透明标识，输入模态和上下文窗口是可选能力，回放状态只允许原适配器恢复。

对 PolyQuota 而言，对应关系是：服务商可以共享“认证、账号、刷新、用量”主干，但每项能力都应显式声明，并由拥有该路由的同一实现执行。

## 4. 注册、替换与释放

### 4.1 唯一路由所有权

`LlmRuntime.registerAdapter(providers, adapter)` 为一组服务商路由注册同一个适配器。初次注册要求至少一个路由，路由名必须非空，适配器返回的元数据必须保留相同标识且包含非空名称。

如果候选路由内部重复，或已被其他适配器占用，注册抛出稳定错误。整个候选集不会部分写入。

这比当前 PolyQuota 在 `RefreshCoordinator` 构造时直接 `new Map()` 更严格：当前重复 `provider` 会由后一个实现静默覆盖，无法发现组合错误。

### 4.2 原子替换

注册句柄的 `replace(nextProviders)` 先完整校验下一组路由，再在一个同步提交段中删除旧路由并写入新路由。读者不会观察到“旧路由已经删除、新路由尚未写入”的空档。

空集合只允许用于已经存在的注册句柄，表达该配置暂时不提供任何路由；释放后的句柄不能再次注册，以免产生无人负责销毁的实现。

### 4.3 生命周期释放

注册实际位于 `ctx.effect()` 中。插件卸载时，disposer 删除它当前拥有的全部路由并发布拓扑变更事件。重新加载插件不会留下旧适配器、重复监听器或悬空实现。

PolyQuota 正式构建阶段不需要运行时热替换服务商代码，但注册所有权仍应明确。应用退出和测试结束时，所有会话、监听器及实现资源应能从组合根统一释放。

## 5. 目录与激活实现分离

DSH 还提供 `registerConfigurableProviders()`：插件可以声明一组“可通过设置激活”的服务商，其中包含展示名称、设置命名空间和设置路径。这个目录与已经注册的适配器路由是两张表。

因此消费者可以区分：

- 已知且可配置，但尚未激活；
- 已注册，可以执行；
- 原先选中，但实现当前已经消失。

会话控制层在目录或模型目录暂时不可用时，保留当前选择并把它作为可恢复选项展示，而不是擅自切换到另一个服务商。

PolyQuota 的服务商管理页同样需要“可展示”和“可执行”两个维度。Grok Build 与 Antigravity 可以作为目录条目出现，但在实现未注册时必须标为不可用，不能让认证请求落到默认实现。

## 6. 动态配置与请求一致性

DSH 的动态适配器可以在设置变化后调整所拥有的路由，但 `prepareCall()` 要求模型能力解析和最终流式请求绑定到同一代实现。这样配置在两步之间变化时，不会拿新版能力去调用旧版端点，或反过来。

这一思想可映射为 PolyQuota 的操作会话：

- `startAuth` 创建的会话固定所属 `providerId`、`offeringId`、认证方式和实现代次；
- `finishAuth` 必须交回同一个实现处理；
- 用量刷新在开始时解析账号对应实现，整个刷新链路保持该引用；
- 注册表更新不能把进行中的认证会话接到另一实现。

当前阶段实现固定，代次问题不突出，但在接口中保留会话所有权可以避免后续扩展时返工。

## 7. 协议严格性

`docs/cookbook/adding-an-llm-adapter.md` 对流协议规定了明确的不变量，例如用量先于结束、工具参数保持原始 JSON、索引稳定、取消信号必须生效，以及错误必须选择抛出稳定错误或发送带错误状态的结束块。

更一般的原则是：统一契约必须覆盖一次操作的完整生命周期。若一个新服务商需要契约外的必要步骤，应先扩展能力接口或明确声明不支持，而不是在实现内部偷偷改变行为。

这对 PolyQuota 的认证尤其重要。API Key、浏览器回调、设备码和本地导入需要成为判别联合，每种交互的开始、完成、取消和公开结果都要闭合。

## 8. 前端与远程边界

`LlmRuntime` 继承远程服务基类，并对目录、服务商列表和模型发现等方法提供远程入口。远程层接收可序列化请求，在服务内部查注册表，不接受实现对象。

远程模型发现还把一次性凭据限定在单次请求中，结果只返回候选模型元数据。错误被转换为稳定的远程错误码和安全详情。

这支持 PolyQuota 继续保持以下约束：

- renderer 只传 `providerId`、`offeringId`、`accountId` 和经过 schema 限定的公开输入；
- 主进程在本地注册表解析实现；
- token、API Key 和 provider 私有请求对象不跨 IPC 返回；
- 错误码稳定，原始响应和秘密不进入公开 DTO。

## 9. 优点与限制

### 9.1 优点

- 插件贡献与生命周期绑定，卸载后不会残留注册项；
- 冲突即失败，多项注册和替换具有原子性；
- 目录、已激活实现和动态能力分层清楚；
- 实现可以提供差异化能力，同时消费者保持统一调用方式；
- 适配器代次与调用绑定，避免动态配置竞态；
- 测试可以注册最小假实现，不需要启动完整应用。

### 9.2 限制

- 任意代码插件显著扩大信任边界和故障面；
- Profile、Bundle、Patch、依赖注入和热重载的完整体系对 PolyQuota 过重；
- 动态卸载要求所有资源都正确实现 disposer，遗漏时问题更隐蔽；
- DSH 的主体是模型推理协议，不能直接替代账号与用量领域模型。

## 10. 对 PolyQuota 的取舍

应采用：

- 唯一 `providerId` 到实现的注册；
- 重复注册和标识不一致时启动失败；
- 先校验完整候选，再一次提交不可变快照；
- 目录声明与可执行实现分离；
- 认证会话和刷新操作固定实现所有权；
- 能力显式声明，不支持时稳定失败；
- 测试使用同一注册 API 注入假实现。

暂不采用：

- 从用户目录加载可执行 JavaScript 插件；
- 服务商代码的运行时热替换；
- 通用 Profile/Bundle/Patch 配置语言；
- 把 Core 的每个内部对象都提升成可替换服务。

最终方案见[跨服务商服务协议设计](./cross-provider-service-protocol-design.md)。
