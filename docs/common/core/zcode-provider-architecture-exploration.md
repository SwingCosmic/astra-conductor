本报告研究 ZCode 如何管理一组预置服务商，并允许用户配置与账号状态在其上叠加。目标不是复制 ZCode 的模型选择系统，而是识别其中适合 PolyQuota 的配置、解析、注册和前端投影边界。

## 1. 结论

ZCode 的核心不是一张静态服务商表，而是一条分层解析流水线：内置发行数据、模板、个人配置、模型规则和账号状态先分别保留，再解析为完整详情视图与可执行注册表。前端可以看到配置来源、覆盖结果和问题；运行时只能取得已经校验且可执行的条目。

这一模式适合服务商数量有限、内置定义是主要来源、用户只在允许范围内覆盖配置的产品。它为 PolyQuota 提供的最重要经验是：

1. 声明、账号事实、解析结果和运行实现不能混成一个对象；
2. 设置页需要保留无效或暂不可用的条目，执行注册表则必须排除它们；
3. 服务商差异应进入结构化字段和问题列表，而不是散落在页面的服务商判断中；
4. 快照修订号和变更事件应成为前端读取一致状态的基础；
5. 内置配置与用户覆盖可以复用同一模型，但秘密和账号授权事实不能作为普通配置覆盖。

ZCode 的完整模型规则系统明显大于 PolyQuota 当前需求，不应整体移植。

## 2. 结构分层

### 2.1 内置发行数据

`packages/provider-node/src/zcode-builtin-release.ts` 把内置服务商、模板和模型规则作为一个带版本、修订号且经 schema 校验的发行单元加载。它不是直接可执行对象，而是解析器的一项输入。

内置配置的主要作用是：

- 提供受支持服务商的默认 API 类型、基础地址、认证方式和展示信息；
- 提供可复用的服务商模板；
- 固定发行版本和修订号，便于判断配置是否属于同一代基线；
- 在进入注册表前拒绝不符合 schema 的数据。

这种做法避免了页面、运行时和设置逻辑各自维护一份服务商常量。

### 2.2 配置与账号来源

`packages/provider/src/sources.ts` 将输入拆成两类快照：

- 配置快照：内置服务商、模板、个人服务商、顺序和模型规则；
- 账号快照：授权、可用性、当前连接和生效时间等运行事实。

账号状态不携带 API Key、token 或请求头。它只表达 `available`、`pending`、`unavailable`、`unknown`、是否有权益以及不可用原因。消费者可以显示差异，但不能通过这些公开事实取得秘密。

分离来源的直接价值是：配置发生变化时不必伪造账号状态，账号刷新失败时也不会破坏用户配置。

### 2.3 解析器

`packages/provider/src/resolver.ts` 接收所有来源并生成两个结果：

- `resolvedProviders`：保留完整配置、来源、账号状态、校验问题、启用状态和可执行状态；
- `registryProviders`：只保留当前有效且可以执行的服务商与模型。

解析顺序大致为：

1. 读取内置服务商和模板；
2. 将账号状态叠加到内置条目；
3. 将模板应用到具体配置；
4. 应用个人配置和个人模型规则；
5. 校验最终 API、认证、模型和选择状态；
6. 产生完整详情与运行注册表两种投影。

覆盖前后的数据没有被抹平。解析结果仍能指出 `templateId`、内置有效配置、个人配置、最终配置、问题来源以及是否可选。这一设计尤其适合设置页诊断。

## 3. 服务商与认证数据

`packages/provider/src/config/provider-data-schema.ts` 使用判别联合表达主要差异。

API 类型是有限集合：

- `anthropic-messages`；
- `openai-chat-completions`；
- `openai-responses`。

认证同样按类型区分：

- API Key；
- Zhipu Coding Plan API Key；
- Zhipu 账号授权及权益状态。

服务商配置还包含服务商分组、图标、API 基础地址、请求头、内置与个人模型标识、顺序和可见性。模板提供本地化名称与一组共享配置。

这里可借鉴的是判别字段和完整校验，不是字段本身。PolyQuota 管理的是账号认证和用量协议，不需要复制模型列表、温度或上下文窗口等模型调用配置。

## 4. 注册表与视图

### 4.1 只读注册表

`packages/provider/src/registry.ts` 将解析后的可执行条目包装为带修订号的不可变视图，提供服务商和模型查询、选择校验、整体替换和变更订阅。

注册表没有边读边修改某个条目的过程。新快照完整解析后一次替换，消费者只会看到旧版或新版，不会看到半套状态。

### 4.2 刷新协调

`packages/provider/src/registry-service.ts` 订阅配置源和账号源，合并短时间内的重复刷新请求，并跟踪来源修订。当内置配置与账号状态不属于可组合的修订时，它保留上一份完整注册表，而不是发布不一致的新状态。

这对 PolyQuota 的启发不是照搬双修订算法，而是明确以下规则：

- 前端一次读取应得到同一修订下的服务商、账号和用量；
- 新状态尚未完整形成时继续保留上一份可用快照；
- 失败通过问题或错误事件表达，不把注册表临时清空；
- 变更通知只在一份新快照真正提交后发布。

### 4.3 面向消费者的两个视图

`packages/provider/src/facades.ts` 区分设置视图和模型选择视图：

- 设置视图保留覆盖层、最终配置、问题和账号状态；
- 选择视图只暴露当前可选项。

`packages/services/src/model-provider/providerFacadeServices.ts` 再把这些视图包装成异步服务接口，供跨进程或 UI 调用。前端不直接操作注册表内部对象。

PolyQuota 也应采用相同方向：服务商管理页可以看见暂不可用的入口和原因；刷新与认证执行只能使用已经绑定实现的条目。

## 5. 绑定方式

ZCode 在应用组合根创建配置源、账号源、解析器、注册表和 facade。运行时不会根据前端传来的任意类名或模块路径装载实现，而是使用已解析的稳定服务商标识查注册表。

这种绑定有三个值得保留的性质：

1. 服务商标识是协议键，不是展示名称；
2. 前端选择只产生稳定标识，不能携带实现对象；
3. 实现可用性由注册表决定，缺失时明确拒绝，不退回到另一个服务商。

## 6. 优点与限制

### 6.1 优点

- 配置来源清晰，内置、模板、个人和账号事实不会互相覆盖到不可追踪；
- 完整视图与可执行视图分离，设置页可以解释失败，运行时保持安全；
- schema 校验、问题列表和修订快照共同减少隐式状态；
- facade 为前端提供稳定异步契约，内部注册表可以独立演进；
- 账号差异作为公开状态传给 UI，UI 不需要猜测权益和可用性。

### 6.2 限制

- 多层覆盖和模型规则带来较高理解成本；
- 解析器、注册表、来源协调和多个 facade 对当前 PolyQuota 来说过重；
- 结构围绕模型选择设计，不能直接等同于用量聚合协议；
- 静态内置集合仍是主路径，不解决任意第三方代码的安全加载问题。

## 7. 对 PolyQuota 的取舍

应采用：

- 服务商声明、账号事实、实现绑定和前端投影分层；
- 完整目录与可执行注册表分离；
- 判别联合表达认证方式及其输入；
- 快照修订号、一次替换和提交后的变更通知；
- 明确的问题列表和不可用原因；
- 应用组合根统一构造与绑定。

暂不采用：

- 模板与个人服务商覆盖；
- 用户自定义任意基础地址和请求头；
- 完整模型规则解析器；
- 运行时从外部目录装载第三方实现。

最终方案见[跨服务商服务协议设计](./cross-provider-service-protocol-design.md)。
